> 본 문서는 발표 준비 Q&A를 요약한 것. docx로 옮겨 슬라이드 대본으로 사용.
> 프로젝트 = 공급망 악성 패키지 **탐지 엔진(pkgsentinel)** + 제안 표준

## 0. 핵심 전략 — "정직함을 무기로"

이 프로젝트의 가장 희귀한 자산은 **자기 검증의 정직함**. "F1 0.94!"보다
"0.94는 평가 하니스 보정이고 출하 엔진은 0.87임을 우리가 측정해 안다"가
심사위원에게 더 강하다. 매끈한 과장 ❌ → 엄밀한 정직 ✅.

**3대 신뢰 축:** ① 데모(검사→서버 실시간 전달) ② S-5 자기검증 정직성
③ 오픈소스=한계극복 + 동작 엔진 뒤에 놓인 manifest 제안.

## 1. 발표 순서 (10분 컷, 데모 영상 1분) — **주력**

|---|---|---|---|

## 1-b. 발표 순서 (22분 풀버전, 긴 슬롯용)

표지(0.5) → 개요(2) → 목적/문제(2.5) → 아키텍처(3) → 오픈소스 활용(2.5)
→ 라이브/영상 데모(3.5~4) → 평가 정직(4) → Manifest(3) → 한계+향후(1.5)
→ 마무리(0.5). **개요-목적-아키텍처를 앞에 세워 "전체가 뭔지" 먼저 각인.**

**순서 논리:** 데모를 평가 앞에(작동 먼저 보여야 수치가 의미), Manifest를 엔진
뒤에("동작 엔진 위에 표준 제안"이 "표준부터 제안"보다 신뢰).

## 3. 세션별 핵심 내용

### 3-1. 아키텍처
레이어드 파이프라인(Stage 0~9) + 2-DB(지식 DB / 분석 캐시 DB). 다이어그램 1장,
큰 그림만. 9단계 상세는 부록.

### 3-2. 오픈소스 활용 — "한계 극복 전략"으로 프레이밍
단순 "라이브러리 썼다" ❌ → **"우리 팀이 못 하는 것을 권위 있는 기반으로 메웠다"**.

| 우리 한계 | 오픈소스로 극복 |
|---|---|
| 권위 있는 위협 지식 부재 | MITRE ATT&CK 431 TTP |
| 알려진 악성 추적 불가 | OSV / OSSF malicious-packages |
| 학습 데이터·GPU 없음 | MiniLM 사전학습 임베딩 |
| JS 파서 작성=수년 | tree-sitter |
| 암호 직접 구현=버그 | SQLCipher AES-256 |
| 정적 분석은 의도 판단 불가 | LLM 3-agent |
| 독자 포맷=생태계 고립 | CycloneDX/STIX/TAXII/Falco (출력 환원) |
| 자작 fixture=과적합 | DataDog 22k 외부 검증셋 |

**슬라이드 한 줄:** "이 프로젝트의 모든 핵심 판단은 우리가 만든 게 아니다 —
공격 분류는 MITRE, 악성 목록은 OSV, 의미 판단은 LLM, 평가 기준은 DataDog이
근거다. 우리는 한 팀이 못 푸는 한계를 인식하고 권위 있는 오픈소스 위에 올라섰다."

Q&A 방어: "오픈소스 의존이 곧 한계 아니냐" → "맞다(트레이드 인정). MiniLM은
범용 임베더, LLM은 외부·유료·비결정적. 엉성하게 재발명하느니 검증된 기반의
제약을 의도적으로 택했다."

### 3-3. 평가 — 4-cell (n=543, DataDog malicious 454 + benign 89)

| | OFF (출하 엔진) | ON (eval 하니스) |
|---|---|---|
| **stub** | P 0.851 · R 0.703 · F1 0.770 · FP 56 | P 0.944 · R 0.667 · F1 0.782 · FP 18 |
| **claude** | P 0.865 · R **0.793** · F1 0.828 · FP 56 | P **0.994** · R 0.773 · F1 0.870 · FP 2 |

**S-5 격차 = ON−OFF precision:** stub +0.093, claude **+0.129** (= 평가 하니스
보정 효과, 출하 엔진이 못 내는 부분).

**세션 5 발표 문구:**
> "정적 단독(출하 엔진) recall **70%** → LLM 3-agent 결합 **79%**(+9pt).
> 실제 침해 패키지 recall **85%**. 그리고 — 우리 평가 도구가 precision을
> **+0.13 부풀리고 있었고, 우리는 그걸 측정해 분리 보고한다.**"

### 3-4. Agentic Capability Manifest (구 AISLOPSQ)
- **정의 한 줄:** "에이전트 보안 원칙(capability 최소화·Rule of Two)을 패키지
  공급망 레벨로 옮긴, 선언형·기계검증 가능한 첫 capability manifest.
  declared-vs-detected diff로 미선언 행위 탐지."
- **포지셔닝:** 보안 *통제*가 아니라 *투명성 관례*. "확정 표준"이 아니라 "제안".
  위협모델(작성자=공격자)을 **맨 앞에** 내세움 = 신뢰 신호.
- **선행연구 대비 빈칸:** CycloneDX/SPDX(목록), SLSA/Sigstore(출처), Scorecard(위생),
  Deno permissions(런타임)은 다루지만 — "이 패키지가 어떤 위험 capability를
  설치 전에 기계검증 가능하게 선언하는가"는 비어있었음.
- **발표/제출 트랙:** 워크숍 페이퍼(SCORED@CCS 등) 또는 OpenSSF/PyPA RFC 제출
  ("표준" 선언 ❌ → "제안"으로). 채택 사례 = 정당성.
- **만들 산출물 5종:** JSON Schema 공개 / 레퍼런스 구현(agentic/) / 자동 생성기 /
  실증 데이터(top-N 자동 생성 + 사건 패키지 declared=∅ 대비 detected) / 위협모델 1페이저.

## 4. 핵심 어필 3종

### 어필 A — "agentic 폭증 → 3-agent 검증 유효" (recall 기반)
**논리 사슬:** ① agentic 패키지 폭증(데이터) → ② 합법 agentic이 악성과 똑같은
위험행위(shell/network/secrets/툴로딩) → 정적 분석 구분 불가(FP 63%) →
③ 의미 수준 판단 필요 = 3-agent 합의 검증.

- **왜 3개:** agentic 패키지가 위험해지는 3경로에 1:1 — **semantic**(자기 코드 의도)
  / **diff**(신뢰받던 패키지의 악성 업데이트, 예: Shai-Hulud) / **dependency**(오염 전이).
- **학술 못:** Nasr "Attacker Moves Second"(2025) — 단일 필터 12종 90%+ 우회 →
  단일 LLM ❌, 복수 에이전트 합의 ✅.
- ⚠️ **정직한 한정:** 3-agent의 진짜 이득은 **recall**(70→79%), **precision 아님**.
  "FP 2개/P 0.99"는 eval 후처리지 코어 엔진 아님. 발표에서 precision을 엔진
  성능으로 말하면 S-5 정직성과 자기모순.

### 어필 B — S-5 자기검증 정직성
대부분 발표는 좋은 수치만 보임. 우리는 "ON/OFF 격차 +0.13을 우리가 측정해
공개"한다 → 성숙도 신호. precision 낮음(약점)을 **가치 명제(유명 패키지 공격
탐지)를 지키기 위한 의도적 trade**로 전환 → 약점이 철학의 증거가 됨.

### 어필 C — 오픈소스 = 한계 극복 (§3-2). S-5 정직성과 한 몸:
"자작 fixture는 과적합된다는 한계를 *알았기에* DataDog 외부 검증셋으로 측정했다."

## 6. 세부 예시 — Shai-Hulud 탐지 (강력한 한 방)

Shai-Hulud 귀속 패키지 25개 실측 (claude):

| | 탐지 |
|---|---|
| **OFF (출하 엔진)** | **23/25 (92%)** |
| ON (eval 하니스) | 20/25 (80%) |

- 탐지: @ctrl·@crowdstrike·@posthog·@voiceflow·@operato·@antv·@nstudio 등 HIGH_RISK
- 놓침: @react-native-aria/menu, /tabs (2개, 약신호)
- **결정적 포인트:** ON(인기도 다운그레이드)에서 @tanstack/* **3개가
  SUSPICIOUS→CLEAN으로 benign-wash** → 80%로 하락. 즉 "유명 패키지 봐주기"가
  실제 침해 패키지를 놓치게 만듦. **우리가 그 룰을 코어에서 제거한 게 옳았다는
  데이터 증명.** "유명 패키지를 봐주면 침해된 유명 패키지를 놓친다."

## 7. precision vs recall (Q&A 대비 깊은 설명)

- **Recall** = 진짜 악성 중 잡은 비율(공격 안 놓치기). **Precision** = 위험이라 한
  것 중 진짜 비율(오탐 안 하기).
- 데이터(OFF): LLM 넣자 TP 319→360(+41, recall↑), FP 56→56(불변, precision 제자리).
- **왜:** verdict_rules가 LLM을 — 자유롭게 **승격**시킴(→recall) 하지만 LLM=BENIGN은
  **약한 신호만** 덮어씀, 강한 신호는 안 깎음(의도적 안전장치) → 강한-합법 FP 잔존.
- precision 개선(eval Rule C)은 "인기+LLM benign이면 강한 신호도 CLEAN" = 위험한
  benign-wash(§6의 @tanstack 사례). 우리가 원칙적으로 거부한 동작.
- **결론 한 줄:** "유명 패키지를 안 봐주기로 했고(원칙), 그 대가로 production
  precision은 낮지만 침해된 유명 패키지를 안 놓친다. LLM은 그 원칙을 지키며
  recall을 올리는 정직한 레버다."

## 8. 검사→서버 데이터 흐름 (데모 근거, 실제 구현됨)

- **인바운드:** `POST /api/v1/analyze` → HMAC 인증(fail-closed) → run_pipeline → verdict 반환.
- **아웃바운드:** worker가 큐 검사 → verdict≥SUSPICIOUS면 WebhookSink(HMAC POST)/
  TaxiiSink(TAXII 2.1)/STIX/Falco로 전송 → sink_log 기록.
- 테스트 존재(urllib mock). **단서:** CI는 네트워크 mock — 라이브 서버 통합
  테스트 없음. 데모 시 로컬 수신 서버 띄워야 "진짜 전달" 시연 가능.

## 9. 피할 함정 / Q&A 방어

- ❌ "세계 최초 표준" → "제안된 관례 / 우리가 아는 한 첫 시도"
- ❌ 합성 fixture F1 0.99를 헤드라인 → 그건 회귀 베이스라인, 헤드라인은 실데이터 OFF
- ❌ "FP 2개/P 0.99"를 엔진 성능으로 → eval 후처리임을 분리 명시
- ❌ 9단계 한 장에 다 → 큰 그림 1장 + 부록
- ❌ 규모로 상용 제품과 비교 → "다른 계층의 빈칸을 메우고 표준으로 연동"
- npm recall 낮음(60%) 선제 고백: "zero-signal POC는 정적 한계, threat-filter(OSV)가 담당"
