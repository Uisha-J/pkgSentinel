# 교수님 피드백 회신 — 초안

날짜: 2026-05-28
용도: 교수님 피드백 메일에 대한 회신 초안 (한 번 더 검토 후 송부)

## 메일 본문 (복사용)

제목: **[캡스톤 7팀] 피드백 의견에 대한 답변 및 보완 계획 (pkgsentinel)**

안녕하세요, 교수님.

바쁘신 와중에 자료를 꼼꼼히 읽어 주시고, 구조적인 부분까지 짚어 주신 의견 진심으로 감사드립니다.
지적해 주신 부분이 저희가 자료를 정리하면서 충분히 부각하지 못했던 지점들이라 큰 도움이 됐습니다. 한 항목씩 답변드리고, 보완 계획을 함께 정리해 보내드립니다.

---

**1) "위험 capability를 선언하고, 이후 실제 동작에서 선언되지 않은 행위를 탐지하는 구조"가 맞는지**

말씀하신 이해가 정확합니다. 보다 정확히는 두 단계로 구성됩니다.

- ① 패키지 작성자가 `pyproject.toml`의 `[tool.agentic]` (npm은 `package.json`의 `agentic` 필드) 에 자신의 패키지가 사용할 위험 capability (예: `net.http`, `shell.exec`, `fs.read`, `secrets.read` 등) 를 사전에 선언합니다.
- ② 저희 도구는 정적·동적 분석으로 실제 capability를 추출한 뒤, 선언된 집합과의 차이를 계산합니다. 선언되지 않은 capability가 탐지되거나, 선언 자체가 없는데 위험 capability가 검출되면 의심으로 처리합니다.

핵심은 **"악성을 직접 탐지"하는 방향이 아니라 "선언되지 않은 행위를 탐지"하는 선언-기반 방어**라는 점입니다. 이 부분이 자료에서 명확히 드러나지 않았던 것 같아 정리해 다시 표현하겠습니다.

---

**2) "차별점은 핵심 설계 자체가 가장 중요하다" — 및 (3) "7-layer 구조가 기존에 없었는지 확인"**

이 두 지적을 같이 말씀드리는 게 정확할 것 같습니다.

솔직히 말씀드리면, **7개 계층으로 패키지를 정적·동적·LLM 으로 다단 분석하는 구조 자체는 새로운 아이디어가 아닙니다.** 선행연구 (Cerebro, LAMPS, DataDog GuardDog, OSSF Package Analysis, Socket.dev 등) 도 다단계 분석 파이프라인을 채택하고 있고, 이 부분에서는 저희가 차별점을 주장하기 어렵습니다.

따라서 발표 자료에서 7-layer 를 차별점의 본체로 제시한 것은 잘못된 강조였습니다. 실제 차별점은 **Agentic Capability Manifest — 즉 "악성을 잡는 방어"가 아니라 "선언되지 않은 capability 사용을 잡는 선언-기반 방어"** 라는 설계 자체에 있다고 정리하겠습니다.

7-layer 는 이 매니페스트 검증을 가능하게 하는 구현(detection backend)으로 재배치하고, 자료의 초반부터 "왜 매니페스트가 필요한가"를 먼저 제시한 뒤 그 뒤에 도구 구현이 따라오는 구조로 다시 작성하겠습니다.

선행연구 중 가장 가까운 것은 Google Capslock 과 Deno permissions 인데, 두 시스템 모두 *(a) 단일 언어·런타임에 한정되거나 (Capslock = Go 정적분석, Deno = Deno 런타임)*, *(b) 작성자 선언이 아닌 도구 추론 결과를 사용* 하기 때문에, *생태계 무관 · 작성자 선언형 · 설치-전 기계검증* 의 세 조건을 동시에 충족하는 시스템은 현재까지 확인하지 못했습니다. 이 빈칸을 명시적으로 표 형태로 정리해서 자료에 추가하겠습니다.

---

**4) 각 계층의 역할 상세 분석 / LLM 기반 유사 분석 사례**

각 layer 의 (a) 입력, (b) 출력, (c) 알고리즘·근거 논문, (d) 잡는 위협 유형 을 표 형태로 정리해 첨부하겠습니다.

LLM 기반 유사 분석은 보내드린 자료 §8.1 에 일부 인용했으나, 비교 항목이 없어 의미가 잘 전달되지 않았습니다. 다음 시스템들과의 항목별 비교표 (LLM 사용 단계, agent 수, 외부 검증 데이터셋, 작성자 선언 지원 여부 등) 를 정리하겠습니다.

- Cerebro (ACM TOSEM 2025): Behavior Sequence + tree-sitter, LLM 단일
- LAMPS (USENIX 2025): PyPI LLM 다중 에이전트
- Mind the Gap (2025): 13개 LLM 비교
- GuardDog (DataDog): Semgrep+YARA+metadata, LLM 없음
- Socket.dev (상용): AI 의심 시 LLM 심층 평가

---

**5) malicious HIGH confidence 판정 기준 및 설계 근거**

이 부분이 현재 외부 자료에 거의 노출돼 있지 않은 것이 사실입니다. 다음 내용을 별도 1페이지 문서로 정리해서 보내드리겠습니다.

- 47-indicator 각각의 가중치 (rule confidence) 와 그 근거
- rule confidence + LLM agent agreement (3-agent 중 몇 개가 동의했는지) 결합 공식
- 최종 verdict threshold (CRITICAL ≥ 80 / HIGH ≥ 60 / MEDIUM ≥ 30) 의 설정 근거 — 실제 측정에서 어느 threshold가 가장 좋은 F1 을 보였는지의 ablation

---

**6) 시스템 구조도 레벨 혼재**

지적이 정확합니다. 현재 구조도가 한 그림 안에서 Python 파일명 (`pipeline.py`), 외부 서비스 (`Claude API`), 저장소 (`SQLCipher DB`), 인터페이스 (`HTTP API`), 도구 (`CLI`, `Extension`) 가 모두 같은 추상화 레벨로 그려져 있어 혼란을 드릴 수 있는 그림이었습니다.

다음과 같이 5개 논리 계층으로 통일해 다시 작성하겠습니다.

- Client Layer — 사용자가 닿는 표면 (CLI / IDE Extension / REST)
- Analysis Layer — 정적 · 행위 · LLM 의미 검증
- Knowledge Layer — Threat Intel · Embeddings · Cache
- Decision Layer — Rule Engine · Manifest Diff
- Reporting Layer — SBOM/VEX · STIX · SIEM webhook

각 박스를 *역할* 단위로만 표시하고, 기술 스택은 박스 안에 작은 라벨로만 부기하는 식으로 통일하겠습니다.

---

**7) "주요 결과가 기존 연구·시스템 대비 실제 우수한지 비교"**

이 부분이 현재 자료에서 가장 약한 지점이라는 점에 동의합니다. 저희가 보내드린 79.3% recall 수치는 DataDog malicious-software-packages-dataset (n=543) 에 대한 측정이지만, **동일한 데이터셋에 대해 GuardDog / Socket / Phylum 같은 비교 대상이 어느 정도 수치를 내는지는 측정해 두지 않은 상태입니다.** 따라서 현재로서는 "우수하다"고 주장할 근거가 부족합니다.

다음과 같이 보완하겠습니다.

- DataDog 데이터셋 (n=543, 동일 fixture) 에 대해 GuardDog 를 동일 환경에서 실측 (OSS 라 가능)
- Socket / Phylum 은 무료 API 한도 내에서 부분 측정 (상용 제약이 있어 전수 측정은 어려움)
- 결과를 같은 metric (recall, FPR, F1) 으로 단일 표에 정리

비교 결과 저희가 더 좋지 않다면 그 자체로도 정직하게 보고하고, 차별점은 정량적 우위가 아닌 "매니페스트 기반 선언-방어 구조" 로 분리해 주장하겠습니다.
